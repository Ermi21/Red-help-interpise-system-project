# Enterprise DB RAG Assistant — Backend

A production-oriented, **read-only** FastAPI backend for an AI chatbot that
analyzes, documents, monitors, and answers natural-language questions about
a company database — powered by a local LLM (Ollama), LangChain, and
ChromaDB.

This repo covers the **backend only**. It exposes REST APIs consumed by a
separate frontend web app and a separate Telegram bot (owned by other team
members) and is fully documented via OpenAPI/Swagger at `/docs`.

> **The single most important property of this system:** it can never
> modify the target company database. That guarantee is enforced at three
> independent layers — see [Read-only enforcement](#read-only-enforcement-defense-in-depth)
> below. This was verified end-to-end against a real PostgreSQL instance
> with a genuinely restricted database role during development.

## Two databases — do not confuse them

This backend talks to **two** different databases, and the distinction is
architecturally load-bearing:

1. **TARGET database** (`TARGET_DB_URL`) — the company's database this
   whole system exists to analyze. Connected with a **read-only** role.
   Never modeled as ORM classes (its schema is unknown ahead of time and
   discovered at runtime); only ever queried via validated raw SQL through
   `app/database/query_executor.py`.
2. **APP database** (`APP_DB_URL`) — this backend's *own* operational
   storage: users, chat history, cached documentation, alerts. Normal
   read/write access, modeled as SQLAlchemy ORM classes in `app/models/`.
   This is infrastructure the backend owns, not customer data.

---

## Read-only enforcement (defense in depth)

Three independent layers, each of which alone would stop a write:

1. **App-level SQL validator** (`app/database/readonly_guard.py:validate_sql`) —
   an allow-list parser (via `sqlparse`) that only permits
   `SELECT` / `SHOW` / `EXPLAIN` / `DESCRIBE` statements, rejects stacked
   /multi-statement queries, and blocks a keyword blacklist
   (`INSERT`, `UPDATE`, `DELETE`, `DROP`, `ALTER`, `CREATE`, `SET`, `PRAGMA`, ...).
   This runs before **every** query issued by `query_executor.py`, including
   ones generated by the LLM (`app/chatbot/sql_safety.py` wraps this with
   markdown-fence stripping for LLM output).
2. **SQLAlchemy engine-level guard** (`app/database/connection.py`) — a
   `before_cursor_execute` event listener on the target engine that
   independently re-checks every statement using a slightly more permissive
   check (`check_connection_level_safety`) so it doesn't break SQLAlchemy's
   own internal reflection queries (e.g. SQLite's `PRAGMA table_info`),
   while still catching real mutations. This exists so that even a future
   code path which forgot to call the validator explicitly is still caught.
3. **The database role itself** — `TARGET_DB_URL` should point at a DB user
   with `SELECT`-only grants (see [Setting up the read-only role](#setting-up-the-read-only-role)).
   On Postgres, the engine is also created with
   `execution_options={"postgresql_readonly": True}`, which puts the
   session itself into a read-only transaction at the protocol level,
   independent of any SQL text parsing.

All three layers were exercised against a real PostgreSQL 16 instance with
an actual restricted role during development — app-level rejection,
engine-level rejection, and a genuine `permission denied` from Postgres
itself were all confirmed independently.

### Setting up the read-only role

```sql
CREATE ROLE readonly_app_user WITH LOGIN PASSWORD 'change-me';
GRANT CONNECT ON DATABASE company_db TO readonly_app_user;
GRANT USAGE ON SCHEMA public TO readonly_app_user;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO readonly_app_user;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO readonly_app_user;
```

## Running locally with Docker

```bash
cp .env.example .env
# edit .env: set TARGET_DB_URL to your read-only role, JWT_SECRET_KEY, etc.

docker compose up -d --build

# first run only: pull the Ollama models this backend expects
docker compose exec ollama ollama pull llama3.1
docker compose exec ollama ollama pull nomic-embed-text
```

The API is then available at `http://localhost:8000`, with interactive
docs at `http://localhost:8000/docs`.

Note: the `TARGET_DB_URL` in `.env` should point at your **existing**
company database — it is intentionally not part of `docker-compose.yml`,
since this backend is a consumer of that database, not its owner.

### Creating the first user

There is no public self-signup (this is an internal enterprise tool). The
very first admin user must be created using the provided script:

```bash
python scripts/create_admin.py --username admin --email admin@example.com --password "CHANGE-ME" --role admin
```

Inside Docker:

```bash
docker compose exec backend python scripts/create_admin.py --username admin --email admin@example.com --password "CHANGE-ME" --role admin
```

After that, `POST /api/v1/auth/users` (admin-only) can provision further
users.

### Typical first-time API flow

```
POST /api/v1/auth/login          -> get a JWT
POST /api/v1/schema/refresh      -> discover schema, generate docs, index into ChromaDB
POST /api/v1/chat                -> ask questions
GET  /api/v1/health/report       -> DB health analysis
GET  /api/v1/recommendations     -> AI recommendations
GET  /api/v1/alerts              -> notification history
```

`schema/refresh` and `chat` require Ollama to be reachable (they call the
chat and/or embedding models). The other endpoints (`health`,
`recommendations`, `alerts`, `auth`) work independently of Ollama.

## Running locally without Docker (e.g. in VS Code)

No PostgreSQL required for local dev — SQLAlchemy is dialect-agnostic, so
SQLite works fine for both the target and app databases while you're
building/testing against your own machine.

```bash
python3 -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env
# minimum required edits in .env for local dev:
#   TARGET_DB_URL=sqlite:///./company_dev.db
#   APP_DB_URL=sqlite:///./app_dev.db
#   JWT_SECRET_KEY=any-random-string

python scripts/seed_dev_data.py          # creates a small sample "company" DB
python scripts/create_admin.py --username admin --email admin@example.com --password "CHANGE-ME"

uvicorn app.main:app --reload
```

Open `http://localhost:8000/docs`, log in via `POST /api/v1/auth/login`,
click **Authorize**, and try the endpoints. A `.vscode/launch.json` is
included if you'd rather run/debug with F5 instead of the terminal.

Swap `TARGET_DB_URL` for a real Postgres URL (see
[Setting up the read-only role](#setting-up-the-read-only-role)) whenever
your team's database is ready — nothing else in the code needs to change.

## Running tests

```bash
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
pytest -v
```

Tests focus on the safety-critical modules: the read-only SQL guard (both
the strict and permissive layers), LLM-generated SQL validation, and
auth/RBAC. `tests/conftest.py` sets the minimum required env vars so the
suite runs without any real database or Ollama instance.

## Notification channels

Configured via `.env` (`EMAIL_ENABLED`, `TELEGRAM_ENABLED`, `SLACK_ENABLED`,
`TEAMS_ENABLED`, `GENERIC_WEBHOOK_ENABLED`). Only `high`/`critical`
severity issues trigger a notification by default (`NOTIFY_MIN_SEVERITY`).
The backend **only sends notifications** — it never takes corrective
action against the target database. Use `POST /api/v1/alerts/test`
(admin-only) to verify channel configuration.

## Known limitations / next steps

- **Migrations**: the app database uses `Base.metadata.create_all()` on
  startup for simplicity. For a real production rollout, switch to Alembic
  migrations.
- **Stored procedure discovery** is implemented for Postgres only
  (`information_schema.routines`); it's a no-op stub on other dialects.
- **NULL-ratio and orphan-record health checks** run `COUNT(*)` scans and
  are capped (max 10 nullable columns per table) to avoid expensive full
  table scans on very large schemas — tune `null_ratio_warning_threshold`
  and the per-table column cap in `app/monitoring/health_analyzer.py` if
  needed.
- **Rate limiting** uses slowapi's in-memory backend by default; point it
  at Redis (`storage_uri=`) for multi-instance deployments.
- **`/healthz` does not actively ping Ollama** (to keep the liveness probe
  fast) — Ollama connectivity issues surface as a `502 llm_provider_error`
  on `/chat` and `/schema/refresh` instead.
- **Docker volume permissions**: the container runs as a non-root
  `appuser`; if your orchestrator mounts `/app/vector_db` or `/app/logs`
  with root ownership, you may need to `chown` them or adjust the
  container's user at deploy time.
